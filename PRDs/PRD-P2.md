# Product Requirements Document - Phase 2 Integration (PRD-P2)

## 1. Executive Summary

This document (`PRD-P2.md`) serves as a targeted execution guide for the uncompleted integration components of SobatWarung Phase 2. While `PRD-BE.md` establishes the overall architecture, a codebase audit revealed that the Node.js backend (`apps/backend`) and the Rust Sync Engine (`services/rust-sync-engine`) currently exist as isolated silos. 

This document defines the strict requirements and architectural blueprints needed to bridge these components. It focuses entirely on:
1. **Synchronous Integration:** gRPC routing from Node.js to Rust.
2. **Asynchronous Integration:** Event-driven communication via Redis Streams.
3. **Agent Integration:** Node.js routing logic for the Privacy-Guard Agent.
4. **Validation:** End-to-End (E2E) testing criteria for the complete system.

*Note: This is an execution-focused document for AI agents. It assumes the base architectures of the Node.js Hono server and Rust axum server are already established as per `PRD-BE.md`.*
## 2. Synchronous Integration: Node.js to Rust gRPC Bridge

### 2.1 Architecture
The Node.js backend acts as a public-facing API Gateway. When a mobile client pushes or pulls offline sync data, Node.js must forward this payload to the Rust Sync Engine for CRDT conflict resolution. This is achieved via gRPC.

```text
┌────────────────────────┐         gRPC         ┌────────────────────────┐
│                        │    (SyncService)     │                        │
│    Node.js Backend     ├─────────────────────▶│    Rust Sync Engine    │
│    (apps/backend)      │◀─────────────────────┤  (rust-sync-engine)    │
│                        │                      │                        │
│ - Validates Auth/JWT   │                      │ - CRDT Merge (yrs)     │
│ - Routes /api/v1/sync  │                      │ - DB Persistence       │
└────────────────────────┘                      └────────────────────────┘
```

### 2.2 Missing Components to Implement
1. **Node.js gRPC Client:** 
   - Add `@grpc/grpc-js` and `@grpc/proto-loader` to `apps/backend/package.json`.
   - Load the `sync.proto` definition (currently located in `services/rust-sync-engine/proto/sync.proto`).
   - Refactor `apps/backend/src/services/sync.service.ts` to forward `syncPush` and `syncPull` logic to the Rust gRPC server instead of using local Prisma logic.

## 3. Asynchronous Integration: Redis Streams Event Bus

### 3.1 Architecture
Agent events (e.g., `INITIATE_GROUP_BUY_POOL`) generated by mobile clients and submitted to the Node.js backend must be distributed to the Rust Crypto Hub and other system agents asynchronously. Currently, Node.js uses an in-memory `EventEmitter`, which is insufficient for cross-service communication.

```text
┌────────────────────┐                          ┌────────────────────┐
│                    │    XADD (Producer)       │                    │
│   Node.js Backend  ├─────────────────────────▶│    Redis Streams   │
│                    │                          │  (Topic: agents)   │
└────────────────────┘                          └─────────┬──────────┘
                                                          │
                                                          │ XREADGROUP (Consumer)
                                                          ▼
                                                ┌────────────────────┐
                                                │                    │
                                                │  Rust Sync Engine  │
                                                │  (Crypto Hub)      │
                                                └────────────────────┘
```

### 3.2 Missing Components to Implement
1. **Node.js Producer:**
   - Refactor `apps/backend/src/agents/event-bus.ts` to publish events to a Redis Stream using the existing `ioredis` client instead of a standard `EventEmitter`.
2. **Rust Consumer:**
   - Add `redis` or `fred` dependency to `services/rust-sync-engine/Cargo.toml`.
   - Implement a background worker in Rust that consumes from the Redis Stream, verifies the cryptographic signature of the event, and triggers relevant Rust-side logic.

## 4. Privacy-Guard Agent Routing

### 4.1 Workflow
The Privacy-Guard Agent runs natively on the mobile client (KMP) but requires the backend to facilitate key exchange and manage encrypted payload states during offline syncs.

### 4.2 Missing Components to Implement
1. **Node.js Routing Logic:**
   - Detect agent events targeted at `targetAudience: 'HUB'` or `targetAudience: 'ALL'` that carry encryption flags.
   - Forward these specific events to the Rust Crypto Hub via gRPC or Redis Streams for key validation before relaying them via WebSockets (`apps/backend/src/ws/agents.ts`) to connected partner devices.

## 5. End-to-End (E2E) Validation Strategy

### 5.1 Acceptance Criteria for Phase 2 Completion
To validate that the silos have been successfully bridged, the following E2E scenarios must pass:

1. **gRPC Sync Flow:**
   - A mobile client (or simulator) sends a `POST /api/v1/sync/push` to Node.js.
   - Node.js successfully passes the payload to Rust via gRPC.
   - Rust successfully merges the payload using `yrs` (CRDT) and returns a success response back through Node.js to the client.

2. **Redis Streams Event Flow:**
   - A client emits an `INITIATE_GROUP_BUY_POOL` event via the Node.js API.
   - Node.js publishes the event to Redis Streams.
   - The Rust engine consumes the event, verifies its cryptographic signature, and logs successful verification.

3. **Privacy-Guard Relay Flow:**
   - An encrypted agent payload is successfully routed through Node.js, validated by Rust, and broadcasted to the correct target devices without exposing plain-text sensitive data in the backend logs.
